易混淆服務與觀念對照

這 24 組是 DOP-C02 最常拿來互相當誘答的組合。每一組先看「選它的關鍵字」，考試時題幹幾乎都會把那個關鍵字寫出來。

1 · CloudTrail vs Config vs CloudWatch

服務記錄什麼選它的關鍵字
CloudTrail誰在什麼時候呼叫了哪個 API「是誰做的」「API 呼叫」「稽核」「誰刪除了…」
Config資源組態的歷史與是否合規「組態變更」「是否符合規範」「不合規自動修復」「資源關係」
CloudWatch執行時的指標與日誌「效能」「使用率」「告警」「應用程式日誌」

三者常一起出現：Config 發現不合規 → EventBridge → Lambda／SSM Automation 修復 → SNS 通知。要「即時」偵測 API 行為用 EventBridge 比對 CloudTrail 事件，不要用「每 5 分鐘查一次 Athena」這種誘答。

2 · SCP vs RCP vs 權限邊界 vs IAM 政策

機制約束對象能不能授權關鍵字
SCP組織內帳戶的 IAM 主體（管理帳戶除外）只設上限，不授權「不論帳戶管理員權限多大都不能…」
RCP
2024 新		組織內帳戶的資源（含來自組織外的主體）只設上限「擋掉組織外部的存取」「只有自家組織能讀這個 S3」
權限邊界單一 IAM 使用者／角色的權限天花板只設上限「讓開發者能自己建角色但不能擴權」
IAM 身分／資源政策主體或資源實際授權一般授權

SCP 拒絕清單 vs 允許清單：要「只能用核准過的服務」＝允許清單，必須移除 FullAWSAccess 再掛只允許核准服務的 SCP。SCP 的 Allow 陳述式不接受 Principal，要排除特定角色請用 Deny ＋ aws:PrincipalArn 條件。

阻擋 root 的標準寫法是 Deny * ＋ StringLike: aws:PrincipalArn = arn:aws:iam::*:root，不是「Allow 非 root」。

3 · Organizations vs Control Tower vs Config 合規套件 vs Security Hub

服務定位關鍵字
Organizations帳戶結構、OU、SCP／RCP、委派管理員「政策護欄」「多帳戶」
Control Tower開箱即用的著陸區：自動建帳戶＋套護欄「新帳戶要有一致基線」「最少維運」→ Account Factory／AFC 藍圖
Config 合規套件一包 Config 規則＋修復動作，可組織層級部署「整個組織統一的合規檢查」
Security Hub彙整 GuardDuty／Inspector／Macie／Config 的發現事項「跨帳戶集中檢視安全發現事項」

4 · 安全偵測四兄弟：GuardDuty / Inspector / Macie / Detective

服務看什麼關鍵字
GuardDuty行為威脅：CloudTrail／VPC 流程／DNS 日誌「遭入侵的執行個體」「異常 API 活動」「可疑網路行為」
Inspector弱點：EC2／ECR 映像／Lambda 的 CVE「弱點掃描」「CVE」「容器映像掃描」
MacieS3 中的敏感資料「個資」「敏感資料外洩」「自訂資料識別碼」
Detective事件根因調查與關聯圖「調查事件的來龍去脈」

Inspector 的 ECR 掃描：基本掃描只比對作業系統套件、推送時掃一次；強化掃描才有持續掃描與語言套件，EC2 強化掃描還需要 SSM Agent ＋ 執行個體設定檔。

5 · CodeDeploy 部署類型與流量切換

運算平台可用部署方式重點
EC2／地端In-place、Blue/GreenBlue/Green 需 ELB；標籤群組是群組內 OR、群組間 AND
LambdaCanary、Linear、AllAtOnce用別名加權；CloudFormation 用 AWS::CodeDeploy::DeploymentConfig ＋ TimeBasedCanary
ECSBlue/Green（經 CodeDeploy）測試用 AfterAllowTestTraffic，正式流量後用 AfterAllowTraffic

AppSpec hooks 順序（EC2 藍綠）：BeforeBlockTraffic → AfterBlockTraffic → ApplicationStop → DownloadBundle → BeforeInstall → Install → AfterInstall → ApplicationStart → ValidateService → BeforeAllowTraffic → AfterAllowTraffic。
「切流量前要先驗證」＝ BeforeAllowTraffic／AfterAllowTestTraffic；DownloadBundle 與 Install 是 CodeDeploy 自己的，不能掛腳本。

6 · Elastic Beanstalk 六種部署策略

策略停機需額外容量回滾
All at once有否需再部署一次
Rolling無（容量下降）否需再部署一次
Rolling with additional batch無（維持容量）是需再部署一次
Immutable無是（整組新機）快，直接丟掉新 ASG
Traffic splitting無是快，且可做金絲雀
Blue/Green（換 URL）無是（兩套環境）換回原 URL

題目說「自動回滾」「失敗影響最小」→ Immutable 或 Traffic splitting。資料庫一定要建在 Beanstalk 環境之外，否則環境刪除時資料跟著消失。

7 · Route 53 七種路由政策

政策用途關鍵字
Simple單一目標—
Weighted依比例分流「1% 流量做金絲雀」「A/B 測試」
Latency導到延遲最低的區域「使用者就近存取」
Failover主／備切換「主區域故障時切到備援」
Geolocation依使用者所在國家／地區「法遵」「在地語系」
Geoproximity依地理距離＋偏置值「調整流量偏向某區」
Multivalue answer回傳多筆健康的記錄「簡易負載分散＋健康檢查」

任何「容錯／自動切換」的選項，沒有搭配健康檢查就是錯的。ALB 沒有固定 IP，只能用別名記錄，不能把 IP 填進 A 記錄。

8 · CloudFront vs Global Accelerator vs ALB vs NLB

層級快取靜態 IP選它的關鍵字
CloudFront七層 HTTP(S)有否「靜態內容」「邊緣快取」「WAF 掛前面」
Global Accelerator四層 TCP/UDP無有（Anycast）「跨區域最低延遲」「非 HTTP 協定」「WebSocket」「固定 IP」
ALB七層無否「路徑／主機路由」「目標群組」
NLB四層無有「極低延遲」「固定 IP」「TCP/UDP」

CloudFront 的原始來源群組只做故障轉移，不做跨區域加權分流。要同時「低延遲」又「跨區域」且是動態內容 → NLB ＋ Global Accelerator。

9 · EventBridge vs SNS vs SQS vs Kinesis

服務模型可重播關鍵字
EventBridge事件匯流排＋規則比對封存可重播「AWS 服務事件」「依內容過濾」「排程」「跨帳戶事件」
SNS發布／訂閱，推送否「扇出通知」「寄信給團隊」
SQS佇列，拉取到期前可重讀「削峰」「解耦」「死信佇列」「重試」
Kinesis Data Streams有序串流，多消費者是（保留期內）「即時串流」「多個消費者讀同一份」「分片」
Data Firehose串流落地否「近即時把日誌寫進 S3／OpenSearch」

降低 Kinesis→Lambda 延遲的三招：增強型 fan-out、提高 ParallelizationFactor、增加分片數。預留並行是「配額上限」不是加速器；加大批次反而增加延遲。

10 · 日誌要查詢時：Logs Insights vs Athena vs OpenSearch

方式資料在哪延遲關鍵字
CloudWatch Logs InsightsCloudWatch Logs近即時「兩種日誌一起查」「最少設定」
AthenaS3查詢時才掃「查 CloudTrail／VPC 流程／ALB 存取日誌」「成本低」「非即時」
OpenSearch自有叢集近即時「全文檢索」「儀表板」但營運負擔高

要「近即時告警」用指標篩選條件＋告警；要「近即時落地 S3」用訂閱篩選條件＋Firehose；CloudWatch agent 不能直接把日誌送到 S3。

11 · CloudWatch 告警設定三個必考細節

設定意義陷阱
Datapoints to alarmM out of N：N 個評估期內有 M 個越界就告警「12 小時內至少 3 小時」＝ 3 out of 12，不是 9 out of 12
遺失資料處理notBreaching／breaching／ignore／missing「沒資料時不要動作」＝ notBreaching
異常偵測 vs 靜態門檻異常偵測學習基線帶狀範圍題目給了明確數字門檻（如 CPU < 2%）就是靜態

停止／重啟 EC2 要用 EC2 動作；跑 runbook 才用 SSM 動作。

12 · Systems Manager 各功能模組

模組做什麼關鍵字
Run Command一次性在機群上執行命令「立刻在所有機器上跑一段指令」
Automation多步驟 runbook（可跨服務）「自動修復」「AWS-RestartEC2Instance」
State Manager持續維持期望狀態「確保代理程式一直都裝著」
Patch Manager修補基準與掃描／安裝「自訂修補儲存庫」「AWS-RunPatchBaseline」
Maintenance Windows只在時段內執行工作「在排定的維護時段內」
Inventory收集已安裝軟體清單搭 Config 規則 ec2-managedinstance-applications-blacklisted 抓禁用軟體
Session Manager免開 SSH 埠的連線「不開 22 埠」「稽核連線」
Parameter Store參數／設定值見第 13 組

題幹出現「在維護時段內修復」時，答案是由 Lambda 註冊一個維護時段工作，不是把 EventBridge 直接指向 Automation runbook（那會立刻執行）。

13 · Secrets Manager vs Parameter Store

自動輪替費用關鍵字
Secrets Manager有（RDS 等有內建範本）按機密計費「自動輪替」「資料庫憑證」「跨帳戶共用機密」
Parameter Store無（要自己寫 Lambda）標準參數免費「設定值」「成本最低」「不需輪替」

跨帳戶／最小權限取用機密：要建客戶受管 KMS 金鑰（AWS 受管的預設金鑰政策改不了），金鑰政策信任 Secrets Manager 並允許該執行角色解密。

14 · RDS 高可用選項（最常被混淆）

選項備援可讀跨區域支援引擎
Multi-AZ DB instance否（純待命）否全部，含 SQL Server
Multi-AZ DB cluster是（2 個可讀備援）否只有 MySQL／PostgreSQL
唯讀複本是可跨區多數引擎（SQL Server 需 EE）
Aurora 全域資料庫是是，典型 < 1 秒Aurora MySQL／PostgreSQL

Aurora 端點：cluster endpoint＝寫入、reader endpoint＝自動輪詢讀取、custom endpoint＝自選成員。既有 Aurora 叢集沒有「開啟 Multi-AZ」的選項，要高可用就是新增 reader 執行個體。全域資料庫若設了 RPO 參數，寫入可能被阻擋，減少次要叢集數量可降低發生頻率。

15 · Auto Scaling 生命週期與更新

機制用途關鍵字
生命週期掛鉤Pending:Wait／Terminating:Wait 暫停等你處理「終止前先把日誌收走」→ Terminating:Wait ＋ EventBridge ＋ SSM Run Command
Instance refresh依新啟動範本逐批換掉現有執行個體「讓現有機器也套用新 AMI／設定」
預熱池預先開好但停機的執行個體「開機太久、擴充太慢」
健康檢查類型EC2 只看硬體，ELB 才看應用程式「應用程式掛了但機器還在」→ 改用 ELB 健康檢查

16 · CloudFormation 的各種武器

功能解決什麼
Change Set部署前先看會改動什麼（尤其是會不會取代資源）
漂移偵測找出有人在主控台手改過的資源
堆疊政策保護特定資源不被更新／刪除
巢狀堆疊重用共用元件、強制部署順序
StackSets一次部署到多帳戶多區域
Git sync（CodeConnections）堆疊直接跟 Git 儲存庫同步，不必自建 CodePipeline
IaC generator掃描既有資源產生範本，把手建資源納管
DeletionPolicy / UpdateReplacePolicy刪堆疊時保留資料庫、S3 等有狀態資源

StackSets 權限模式：自我管理＝要自己在每個目標帳戶建 IAM 角色；服務管理＝整合 Organizations，可開自動部署讓新帳戶自動套用。題目說「現有與未來所有帳戶」就是服務管理＋自動部署。

17 · CodePipeline 的執行模式與結構

項目說明
V1 vs V2標籤觸發、觸發篩選條件、變數、QUEUED／PARALLEL 模式都只有 V2 有
SUPERSEDED預設：新的執行會取代還在等待的舊執行
QUEUED排隊，等前一次跑完才跑下一次
runOrder同一個 stage 內數字相同＝並行，不同＝依序
跨區域動作每一個有動作的區域都必須有自己的 artifact bucket

18 · 備份、複寫與災難復原

DR 策略RTO／RPO成本長相
Backup & Restore數小時最低只有備份
Pilot Light數十分鐘低資料持續複寫，運算關機
Warm Standby數分鐘中縮小規模但一直在跑
Multi-Site Active/Active近乎零最高兩邊都在服務流量

「近即時複寫」：DynamoDB 全域資料表、Aurora 全域資料庫、S3 跨區域複寫。AWS Backup 與快照最快只到小時級，看到「每 30 秒備份一次」「每 5 分鐘複製快照」就是誘答。

19 · 儲存四選一：S3 / EBS / EFS / FSx

協定共享關鍵字
S3HTTP API是「物件」「靜態網站」「資料湖」
EBS區塊單一執行個體（io2 可多掛）「開機磁碟」「資料庫磁碟」
EFS只有 NFS是，多 AZ「Linux 多台共用」「Lambda 共用儲存」
FSxSMB／Lustre／ONTAP是「Windows SMB」「多協定」「次毫秒延遲」「HPC」

20 · 跨帳戶監控：OAM sink/link vs 跨帳戶角色

CloudWatch 跨帳戶可觀測性的正確順序：

  • 監控帳戶建立 OAM sink，在 Select data 勾選 Logs／Metrics／Traces，指定來源帳戶或組織 ID。
  • 要連結整個組織時，CloudWatch 主控台會產生一份 CloudFormation 範本，由管理帳戶用 StackSets 部署到全組織建立 link。
  • 查詢者在監控帳戶用掛 CloudWatchLogsReadOnlyAccess 的角色即可。

實際動作是 oam:CreateSink／oam:CreateLink 與各資料類型的 logs:Link、cloudwatch:Link。看到 iam:CreateSink 這種寫法直接排除。

21 · ECS 任務啟動後馬上停止，可能原因

原因症狀
日誌群組不存在ResourceInitializationError，容器根本起不來（awslogs 驅動預設不會自動建群組）
必要容器結束essential container 退出 → 整個任務停止
目標群組健康檢查失敗任務起得來但被 ECS 停掉並重啟，部署卡住
執行角色權限不足拉不到 ECR 映像或讀不到 Secrets

任務執行角色（拉映像、送日誌）vs 任務角色（應用程式自己呼叫 AWS API），兩者是不同的角色，常被互換當誘答。

22 · 成品與映像：CodeArtifact vs ECR vs S3

放什麼關鍵字
CodeArtifactnpm／pip／Maven／NuGet 套件「代理公開套件來源」「內部共用函式庫」
ECR容器映像「映像掃描」「生命週期政策」「跨區複寫」
S3任何檔案「公開下載」→ 記得關閉成品加密，SSE-KMS 物件無法匿名讀取

23 · ABAC：PrincipalTag vs ResourceTag

「每個人只能存取自己部門／專案的資源」的標準寫法：

寫法正確嗎
"ec2:ResourceTag/department": "${aws:PrincipalTag/department}"正確一條政策涵蓋所有部門
"aws:PrincipalTag/department": "${aws:ResourceTag/department}"方向寫反
"ForAllValues:StringEquals": {"aws:TagKeys": [...]}只檢查鍵，不比對值
"ec2:ResourceTag/department": ["d1","d2","d3"]寫死值，新增部門要改政策

sts:AssumeRole 要放在使用者（主體）的身分政策裡，不是放在被承擔的角色上。

24 · 「最少營運負擔」題型的通用判斷

  • 有受管功能就不要自己寫 Lambda 解析（例：Config 受管規則 > 自己解析 Inventory 檔）。
  • 有原生整合就不要自己接膠水（例：CloudFormation Git sync > 自建 CodePipeline）。
  • 有組織層級設定就不要逐帳戶部署（例：委派管理員＋自動啟用 > 邀請制＋StackSet 接受邀請）。
  • 選項裡出現「自行維運叢集／自架設備／第三方軟體裝在單一 EC2」通常是誘答，尤其題目同時要求「高可用」。
  • 選項出現「每 5 分鐘輪詢」「排程查一次」而題目要「近即時」，直接排除。
